# 1. 现在确定做什么

**确定一条主线：建立一个共享的、随运行状态更新的轻量时间分布预测器，预测混合工作负载中空闲上下文下一次合法 KV 需求的剩余时间；接入固定缓存决策器，验证它相对强经验分布基线的增量价值。**

无需先在五个方案中选择，也不把五个完整系统拼起来。上一份报告是候选方法地图，没有替你做足够明确的工程取舍。本方案替代其中“先逐类场景探索、再逐个选择模型”的推进建议。

研究对象不是某种工具的独立平均耗时，也不是整个 Agent 的任务完成时间。对象是当前空闲的一个 owner–兼容前缀关系，问题是：**从现在起，它在未来 0.1 秒、1 秒、10 秒等窗口内被合法访问的概率分别是多少？**

拟定题目：**面向混合 Agent 工作负载的状态条件 KV 复用时间预测**。

拟检验的贡献：在工具、执行阶段和并发负载不断变化时，共享模型能否利用当前状态，对合法需求时间给出比工具参数聚类经验分布更准确、可校准的预测，并改善同一缓存策略的决策。混合场景、elapsed、生存分析各自都不是自动成立的创新点。

第一轮明确采用：

- 一个主模型：离散时间竞争风险预测器，以浅层多分类 GBDT 实现。
- 一个预测终点：下一次合法 **cache lookup**，与当前 LeasePath 标签一致。
- 一个服务环境：现有单服务器 FCFS、HBM-only、固定模型/兼容配置。
- 一个应用验证：固定的概率评分淘汰器；预测器切换时其他机制相同。
- 一项关键对照：CacheWise-style 参数条件经验分布＋elapsed 更新。

不同时建设新的 TTL 优化器、队列仿真模型、完整工具调用树、强化学习或 GPU/CPU/NVMe 多层缓存。并行与队列通过当前可见特征进入同一个模型，数据确有不足时才扩展结构。

# 2. 原来五个方案如何归位

| 原报告方案 | 本次明确安排 | 对主线的作用 |
|---|---|---|
| A：条件经验分布 | 必做基线 | 回答复杂模型是否真的比简单统计好 |
| B：分位数树/AFT | 不再单独开发一套 | 沿用轻量树模型思路；主输出统一成事件时间分布 |
| C：竞争风险 | 主模型的输出与训练方式 | 同时处理合法需求、明确终止和观察截断 |
| D：阶段/依赖分解 | 首版只取可见状态特征 | 支持混合场景；暂不做独立阶段模型和分布卷积 |
| E：决策感知 | 固定评估接口 | 衡量预测是否改变有价值的动作；暂不学习策略 |

因此它们的关系是：**一个主模型、一组逐步增加的输入、几个对照基线、一个固定验证策略。** 没有五个场景分类器，也没有五个专家模型和路由器。

# 3. 混合场景为什么可以用同一个模型

## 3.1 场景是状态组合，不是互斥标签

同一个上下文可能正在等测试工具，测试包含重试，另一个子任务并行执行，服务端还存在排队。无需把它划为“测试场景”“并行场景”或“排队场景”中的唯一一类。模型看到的是这些状态的组合。

例如，下表仅说明输入方式，不是实验结果：

| 当前上下文 | 当前工具/阶段 | 已等待 | 未完成依赖 | 队列状态 | 使用的模型 |
|---|---|---:|---:|---|---|
| A | 文件读取 | 0.02 s | 1 | 短队列 | 同一个共享模型 |
| B | pytest 执行 | 2 s | 1 | 短队列 | 同一个共享模型 |
| C | 两个子任务汇合 | 3 s | 2 | 长队列 | 同一个共享模型 |
| D | 工具已结束、请求已入队 | 0.5 s | 0 | 长队列 | 同一个共享模型 |

更新也不需要切换模型。C 的一个子任务完成后，更新依赖计数、剩余分支摘要和阶段，再重新预测；D 被实际 dispatch/活动引用接管后，交给现有 active 机制保护。

## 3.2 同时处理两种“混合”

**工作流内部混合：** 一个任务先检索，再测试，再并行等待，最后生成结果。每次决策都按当时可见状态生成快照，同一任务可以跨越多个状态。

**工作流之间混合：** 快工具会话、长测试会话和分支汇合会话同时竞争缓存。模型共享训练，决策器在同一真实竞争候选集中比较预测。

“共享模型”不保证对任何未见组合都有效。实验必须包含组合变化、工具占比变化和负载变化，检验它是否比各工具独立统计更能泛化。

# 4. 模型具体怎么做

## 4.1 预测单位和标签

一个样本对应“某 owner 的兼容前缀在某个当前时刻仍处于 idle”。用已有 `idle_episode` 标识关联，特征和未来标签独立存储。

从快照时刻往后，记录最早发生的结局：

1. **U：legal demand。** 下一次 cache lookup 的输入确实需要这个兼容前缀。即使 KV 已被淘汰而导致 miss，仍属于 U。
2. **D：retire。** 该 owner–前缀复用关系被明确、永久结束。结束一个 owner 不代表共享物理块整体死亡。
3. **C：right censoring。** 观察结束仍未看到 U 或 D。C 只告诉模型这段时间内没有事件，不训练成“以后不会复用”。

工具结束、timeout 返回错误、一次重试，都不自动产生 D；只有确切结束复用关系的事件才算。下一次请求没有匹配旧前缀，也不自动证明它永远不会重返。

首版目标固定为 lookup，避免同时学习 tool/ready/lookup 三个模型。工具完成与 ready 用于分析误差来源。以后迁移到另一调度器时，需要重新校准 lookup 分布，因为其中包含策略相关的队列延迟。

## 4.2 输入：先把低成本可见信号收齐

| 组别 | 首版字段 | 缺失处理 |
|---|---|---|
| 工具/参数 | tool name、命令族、输入长度、已知规模档位、显式 timeout | 未知类别与缺失标记；不调用 LLM 补猜 |
| 动态状态 | elapsed、phase、已发生 retry 数、当前是否已入队 | 无 phase 探针就缺失，不根据最终日志倒填 |
| 短期历史 | 过去 3/8 次可用的工具耗时摘要、同类调用中位数、最近失败情况 | 仅使用当前时刻之前已完成的记录 |
| 已观测依赖 | 未完成数量、已知 AND/OR 等待语义、分支工具族计数、elapsed 的 max/mean | 无法获知子任务时用 unknown；不用未来完整 DAG |
| 服务状态 | 当前队列长度/已观测工作量、KV 压力、当前执行状态 | 不输入未来队列、未来淘汰或未来命中 |

队列特征在首版中直接进入共享模型；不用当前队列长度机械推算将来排队时间。并行特征使用固定长度统计，不引入 GNN。合法前缀本身用于标签与资源核算；完整 token 内容不进入第一版预测器。

将特征分为公共可用组与增强探针组，记录真实可用性。新模型和强基线首先比较同一可用元数据，随后再消融新增状态，区分模型改进和额外观测信息的作用。

## 4.3 输出：一个合法的时间分布

采用 12 个时间窗口，初始右端点为：

`0.01, 0.03, 0.1, 0.3, 1, 3, 10, 30, 60, 120, 300, 600` 秒。

这些是工程初值，数据审计后只能在开发阶段调整。超过 600 秒尚无结局的样本保留 tail 状态；不能把 tail 解释为永不复用。

对于每个区间 k，模型输出“此前尚无事件”的条件下三种概率：复用、终止、继续等待。令它们为 hU(k)、hD(k)、h0(k)，通过多分类 softmax 保证和为 1。

模型只需训练一个共享函数：

`GBDT(当前状态特征, 相对时间区间 k) → [hU(k), hD(k), h0(k)]`。

把区间概率累积，得到每个时间窗内先发生 U 的概率 F_U，以及先发生 D 的概率 F_D。F_U 自动随时间递增，F_U＋F_D 不超过 1；剩余概率表示截至该窗口仍未发生两种结局。

具体初始模型配置：LightGBM multiclass，约 100 棵树、15 个叶子、CPU 推理。用单个共享树模型和时间区间特征实现，不训练 12 个独立模型。规模只是起点，实际按开发误差与完整预测开销选择。

这仍是离散 hazard 模型：每个未来区间使用快照时刻已经知道的状态。不能把未来实际 phase 或队列填入未来区间。新状态真的出现后再生成新快照、更新预测。

如果训练集中 D 极少，先固定 D 分支为开发先验或零并标注支持边界，训练 U/等待版本；不要制造终止样本来维持形式。接口和研究主线保持一致，复杂度由真实事件决定。

## 4.4 训练和更新

一个在第 k 个区间发生 U 的样本，对此前区间提供“等待”，对 k 提供“复用”；D 类似。删失只提供已经完整观测到的区间，落在删失点之后的区间全部不训练；首版对最后一个部分观测区间不计 loss，明确这是丢弃部分信息的保守离散化。

每个 episode 在开始、可见阶段/依赖变化，以及对数间隔的等待检查点产生快照。初期限制每个 episode 最多约 8 个训练快照，固定采样种子；按 episode 平衡权重，防止长工具重复样本支配训练。所有快照随完整 session/项目一起划分。

运行时在以下时刻更新：进入 idle、工具/依赖/队列状态发生有意义变化、进入下一个等待检查点、缓存发生实际竞争且旧预测过时。缓存预测结果，属于同一关系的多个块共用一次预测。周期刷新频率需要测量，不能声称固定微秒级开销。

新工具、未知组合或近期校准恶化时退回按工具/全局经验分布；不依赖树模型 softmax 的“高置信”来识别分布外输入。第一轮冻结模型参数做测试，历史统计可按时间因果更新；不在测试期间用未来标签重新训练。

# 5. 如何验证预测能用于缓存

## 5.1 固定一个简单评分器

主实验保持 FCFS、模型、容量、active headroom 与生命周期清理一致，仅在缓存空间不足时对可淘汰的 idle KV 候选评分。确定 dead 的部分先处理，active 引用不可淘汰。

对合法的候选前缀片段 c，采用：

`score(c) = miss_cost(c) / marginal_bytes(c) × Σ_k w_k × ΔF_U,c(k)`。

其中 w_k 随区间时间递减，默认 `exp(-midpoint(k)/H)`，H 只在开发集选择一次；ΔF_U 是落在区间 k 的复用概率。score 高的优先保留，低的优先淘汰。超出预测窗口的贡献默认忽略，并明确这是有限窗口目标。

这一评分器只是用来统一比较预测器的固定启发式，不是拟议算法新颖性，也不宣称 JCT 最优。它把“什么时候复用”与“miss 有多贵、需要多少空间”连接起来；第一版不增加 lease、prefetch 或调度优先权。

前缀有祖先依赖，不能直接把所有物理块按分数独立乱删。沿用后端合法候选与前缀连续性约束，按一组实际可回收片段计算边际字节和重算成本。共享块只释放无活动引用、无其他保护引用的真实可回收部分。

多个 owner 的共享块，第一版可用各 owner 的 F_U 最大值作为保守聚合代理；它是至少一个 owner 复用概率的下界，不是精确 union。固定同一代理用于所有预测器，单列共享子集效果。预测和任务标签按 owner，容量按物理并集，不能重复计费或因单个 owner retire 删除共享块。

现有 `source_replay.py` 支持固定 TTL 与有限脚本，尚未提供这一实时预测接口；需要增加严格因果的 observer/policy callback。控制器可见当前状态，未来工具时长/请求列表只留在环境推进器，不传给策略。此项是明确实施工作，不把“已有回放器”说成已经支持新算法。

## 5.2 两层比较，避免混淆

**比较一：预测器比较。** 所有时间分布预测器接同一评分器。经验分布也转换成各区间概率；相同状态下比较近期复用概率、校准、排序和 JCT。

**比较二：系统机制比较。** 增加 LRU、dead-first LRU/MRU、调优 fixed TTL、CacheWise-style 原始条件预期时间排序、Continuum-style TTL。明确名称为同后端机制对照；没有实现其完整交换/调度/预取时不声称完整复现。

步距只在确有结构信息的测试子集比较；未知结构不能用未来 trace 偷算步距。未来真值只作为离线诊断，不是在线特征，也不自动构成 JCT 最优上界。

# 6. 需要怎样的数据才能快速推进

## 6.1 第一批数据组成

先收集三类真实工具轨迹：文件/检索等短调用、测试/编译等长调用、包含实际并行等待的复合任务。每条完整 workflow 允许连续跨越这些状态，不将其人为固定成纯工具类别。

pilot 初始目标为 60–100 条完整 workflows、约 1,000 次以上工具事件，来自多个独立任务来源；这是开发与可行性检查规模，不是最终论文样本量。最终数据量由分组数、长尾风险集、校准区间和系统重复误差决定。

使用三种测试变化：

- 开发组成：短工具与长工具均有覆盖，含并行依赖。
- 组成变化：提高长工具/并行任务的比重，保留已见工具族。
- 环境变化：独立运行时改变 runner 负载或服务到达压力；另保留未见项目。

具体比例先由开发数据的可用覆盖确定再冻结；自然组成与人为重加权组成分开报告。组合 trace 进行系统回放时仍按真实依赖推进，不能把工具事件随机打散成独立调用。

## 6.2 公共数据与现有项目如何使用

TraceLab 用于公开数据上的工具时长长尾、历史和状态可预测性验证；先审计固定 release 的字段。没有兼容 token 前缀或服务端 lookup 的记录，只能标为 inter-request gap 代理任务，不能混入精确 KV 标签。

CacheWise/CATraces 优先用于强基线核验；缺失原始参数时使用共同可用的命令类别特征，并写明无法复现 TF-IDF 的限制。原始参数可获得的自采集合上，再做完整参数聚类对照。不能拿弱化基线宣称超越原论文。

已有 BFCL 本地工具时间很短，不足以成为主预测数据。沿用其兼容前缀、原生 KV、成本校准和回放基础设施；受控加等待时间的实验只作机制验证，清楚标注人工干预。

训练/测试按完整来源项目和时间隔离；参数词表、聚类、历史分组、模型超参数和 H 均在开发期冻结。自主 Agent 生成与固定轨迹回放是不同证据，第一轮优先固定轨迹以隔离缓存因素。

# 7. 只回答三个研究问题

**RQ1：混合状态中，时间到底有多少可用信息？** 相同步距/同工具下，条件时间分布是否不同；强经验分布的错误集中在哪里；当前阶段、依赖和队列能解释多少。

**RQ2：一个共享模型能否在组成与环境变化时保持有效？** 比较 CacheWise-style 与主模型，重点看 0.1/1/10 秒等窗口的 Brier score、校准和决策候选内的排序错误。零删失与有删失子集分别报告；观察未知的窗口用合适的删失处理，而非直接当负例。

**RQ3：增量预测信息是否带来净系统收益？** 固定评分器与后端，比较平均/P95 JCT、重算时间、缓存 miss 和预测/状态采集成本。将容量从低压力扫到竞争区、再到过载，保留无收益区。

核心消融只做四项：

| 模型版本 | 用途 |
|---|---|
| 强经验分布：工具/参数＋elapsed | 直接先行工作对照 |
| 共享 GBDT，仍只用同一组特征 | 分离模型本身贡献 |
| 加 phase、短历史与已观测依赖 | 检验混合执行状态的信息价值 |
| 再加当前队列/压力 | 检验 lookup 目标所需的服务状态价值 |

事件/删失处理另作针对性消融，不必把所有特征组合全排列。retire 清理对所有策略相同；否则会把生命周期收益误归因于时间模型。

最希望得到的四张图：同工具/步距的时间差异；跨组成测试的窗口校准；各状态特征带来的增量；相同决策器下容量—JCT—开销的变化。

必须重新推进闭环：缓存改变服务时间之后，后继工具启动、ready、队列和 lookup 均变化。单条基线 trace 上更低的预测误差不能代替这一系统验证。

| D5–D6 | 训练共享 hazard GBDT；按 episode 权重；完成基本校准 | 一个模型、同输入比较、状态特征消融 |

| D8 | 跑混合组成、容量和负载扫描，冻结所有开发选择 | 第一轮预测指标和 JCT 对照 |
| D9 | 独立时间/来源测试；测更新与控制开销；关键配置原生检查 | 泛化结果、开销分布、校准偏差 |
| D10 | 汇总增益/失败/数据限制，决定扩大还是收缩 | 四张主图雏形和推进判断 |

建议新增产物：

- `docs/prediction_contract.md`：快照、U/D/C、字段可见性与切分约束。
- `src/leasepath/prediction_dataset.py`：从事件导出快照和独立标签。
- `src/leasepath/reuse_predictor.py`：统一 `predict(features, horizons)` 接口，含 ECDF 与 GBDT。
- `scripts/train_reuse_predictor.py`：开发拟合、冻结、校准和来源哈希。
- `scripts/evaluate_reuse_prediction.py`：窗口概率、删失与分组误差。
- `source_replay.py` 的当前状态回调：独立于环境未来事件，供固定评分器调用。

上述为拟新增/修改项，本次研究方案没有将它们标成已实现。

# 9. 怎样判断值得继续

前六天优先回答：**在同一批真实混合轨迹上，当前状态是否比 CacheWise-style 的元数据＋elapsed 提供稳定的额外信息？** 这一步不要求先做完整新缓存系统。

继续扩大研究需同时满足：

1. 独立来源/时间测试中，关键时间窗或实际竞争候选的预测确有改善。
2. 固定策略下，改善体现为净系统收益，且不是新增调度权限、retire 清理或少算开销造成的。
3. 组成变化后仍有可解释的适用区，失败状态能够被识别并合理退回。

项目约 5% 平均 JCT 可作为工程筛查目标；若改进小于测量与回放误差，结论保持待定。若预测变好而系统不变，优先检查自然命中和决策空间，不立刻换深网。如果只有特定工具族有效，可以收缩为有明确边界的研究结果。

不能仅凭弱未来启发式找不到收益宣布方向无效；同样，也不能因为“混合很复杂”就预设新模型必有优势。

# 10. 与先行工作的关系

CacheWise 已覆盖工具参数与 elapsed 条件剩余时间；Continuum 已覆盖时长分布和 TTL；KVTether 已覆盖生命周期管理。因此本方案把这些设为强基线与共同基础，拟检验的差异是**共享的合法事件时间模型在混合运行状态、观察截断和组成变化下的增量价值**。

引用与原文定位沿用[调研报告](kv_reuse_time_prediction_survey_2026-10-27.md)，尤其 [CacheWise §5.2–5.3](https://arxiv.org/html/2606.16824v1)、[Continuum §4–5](https://arxiv.org/html/2511.02230v7)、[KVTether §4–6](https://arxiv.org/html/2609.39819v1)。当前只是可执行且可证伪的研究方案，不代表已验证优越性或完成最终查新。
