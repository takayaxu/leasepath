# 从预测评估推进到缓存策略与端到端时间

2026-11-08（Asia/Shanghai）。用户要求下一阶段面向端到端完成时间减少。本轮已新增因果缓存管理层，并将冻结的条件经验和 GBDT 接入相同淘汰规则，完成 10 道内部测试母题的压力回放。**预测接入缓存决策已实现；32B 真机多 owner KV 和端到端 JCT 收益尚未实现／测量。**

后续记录：同日已完成 [真实多 owner KV 与端到端系统验收](qwen_cache_stage2_2026-11-08.md)，54/54 次任务正确。本文保留当时元数据回放的范围和后续计划，不将回放收益改写为真机收益。

## 目标与当前缺口

目标链路是：工具运行期间释放模型执行权 → 多个会话共享有限 KV 池 → 缓存压力下优先保留可能近期复用的前缀 → 下次请求少做 prefill → 完整 Agent 提交到最终正确答案的时间缩短。工具计算、模型解码、排队、管理和预测开销均纳入最终计时，不能只报告命中率。

实查 `native/qwen_data_cuda.cpp` 的 `cp.n_seq_max=1`、`cells()`、`request()` 均只处理 sequence 0；`scripts/run_qwen_data_pilot.py` 每母题开始会 `engine.clear()`。这个后端能核查单会话真实 KV 复用，不能直接管理多个空闲 owner；串行清空模式缺少缓存竞争。旧 `source_replay.DeviceExecutor` 固定于另一版 3B/native 布局与成本，不能当作当前 32B 后端已支持。

资源快照实测 10 张 V100 32GB，GPU 0–4 有原任务，5–9 空闲约 4MiB。本阶段没有启动模型；后续仍优先沿用已验收的 5/6/7，启动前重新检查。RAM 可用约 273GiB，磁盘剩余约 5.4TiB。旧报告卡数不能代替实际检查。

## 已实现的策略接口

新增 `src/leasepath/predictive_cache.py`，接收 owner、当前前缀块、当前时间和九字段因果快照。预测器只收到 `features`，没有下一请求、剩余时间、真实工具总耗时、最终结局或完整回放对象。当前 owner 与实际块的映射由模型外控制器维护。

策略在真实容量压力入口才计算，不在无压力时逐 tick 调用预测器。输入历史已观察状态的 elapsed 随当前时钟增长，不推断未来工具结束。策略不使用硬 pin/lease 阻塞已就绪请求；保持 active 块不可淘汰，活动并集超限明确拒绝供调度器排队。淘汰只移除前缀树的叶块，避免保留失去祖先而无法复用的后缀。释放／retire 一个 owner 不删除其他 owner 共享物理块；resident 数据在压力下才实际淘汰。

比较四种策略：

1. LRU；
2. 显式已 retire 块优先、其余 LRU（强对照）；
3. 条件经验预测的近期复用价值；
4. GBDT 预测的相同近期复用价值。

两种预测策略均使用预定 `F_U(3s)`，共享块取仍有合法关系的 owner 概率最大值，按相同 block bytes 归一，低分先淘汰，LRU 打破并列。最大值是避免共享字节重复计数的保守优先级代理，**不是独立 owner 联合概率**。它未乘上实测重算成本、关键路径权重或内存机会成本，因此不是已证明最优的时间目标；下一阶段应先测 prefill 曲线再评估是否需要成本修正。模型不支持的当前候选状态使本轮淘汰回退到同一 retire-first LRU，不用测试标签补值。

## 固定压力回放

输入仍是上一轮 40 训练／10 测试划分：只加载 40 题训练的模型，只回放 10 道测试题。计划在运行前冻结到 `configs/prediction/qwen_cache_stage1_2026-11-08.json`。32、64、128、256 个逻辑块，每块 128 tokens；四种策略全报告，没有挑最佳容量／时间窗。

从真实后端 lookup token IDs 生成兼容前缀块，保留至少 1 个 token 重算 logits。用每题实际顺序、实际请求服务时长及 release 到下个 ready 的观测间隔，构造十个会话同时到达、单模型 FCFS 服务、工具间隔可重叠的压力环境。未来请求与时刻仅由环境推进器持有；缓存策略不接收它们。工具／阶段更新来自相对 release 的已观测快照，未添加 sleep、伪造新 U/D/C 或新训练样本。

**服务时长在所有策略下固定为原测值**，这只能诊断命中和决策差异。服务速度变化本应反过来改变就绪／排队时间，因此本轮不输出反事实 JCT，不根据 token 减少推算端到端加速。该环境是构造压力回放，不是自然到达流量或完整实时 Agent 运行。

总共 31 个实际请求、49,980 个输入 tokens，逻辑结果如下：

| 容量（128-token 块） | LRU 未命中输入 tokens | retire-first LRU | 条件经验策略 | GBDT 策略 |
|---|---:|---:|---:|---:|
| 32 | 38,076 | 37,820 | **31,420** | **31,420** |
| 64 | 37,820 | 31,420 | **21,948** | **21,948** |
| 128 | 16,444 | 16,444 | 16,444 | 16,444 |
| 256 | 16,444 | 16,444 | 16,444 | 16,444 |

32 块时预测策略相对 retire-first LRU 少 6,400 个未命中输入 tokens（16.9%）；64 块少 9,472 个（30.1%）。这是元数据缓存下需要重算的输入 token 差异，不是设备实测 prefill 节省或完成时间改善。128／256 块无淘汰，控制器也不调用预测器，四种策略完全相同。

条件经验与 GBDT 在所有容量下的逐请求命中数和逐次淘汰块序列完全相同，虽然预测概率和 Brier 不同。预测精度排名不自动转为策略收益排名。压力配置中两者分别调用 181／159 次，GBDT API 合计开销约为条件经验的 7 倍；计时是描述性 CPU 开销，未计入固定服务模拟时钟。共享概率相同或能产生相同排序时，应优先验证成本更低的条件经验，仍保留 GBDT 配对对照。

## 下一步：真实 KV 后端与端到端配对实验

第一步改当前固定 llama.cpp 32B adapter，让它维护多个 owner 的输入前缀和真实序列，单请求模型执行仍可串行，工具异步推进即可产生重叠。需要真实 enact 控制器动作（复用、删除、共享、回收），容量约束覆盖 idle KV、active 输入和生成 headroom，固定逻辑 payload 上限；同时报告实际 device 分配／预留字节，不能用“逻辑淘汰”冒充显存释放。当前 16K context 对回放 256×128 的容量并不充分，必须实测调整物理池／headroom，不能直接照搬元数据容量。

后端先通过两个交错 owner 的有限验收：A→B→A 仍有真实命中；强制淘汰后 A 真正重算；retire 一个共享 owner 不破坏另一个；active 不被淘汰；实际 prompt token、命中／executed prefill 和物理 cell ownership 完全一致；冷／热路径生成与质量一致；异常退出不遗留可复用伪状态。新增模型调用应建立独立封顶账本，旧 331 次账本不追加。本轮尚未启动这项真机验收。

第二步测同模型不同前缀长度、命中比例、驻留规模的实际 prefill／decode 时间。不要把缺失 token×常数当作最终加速；当前题目输入约 1–2K，工具和解码可能主导完成时间，要先量出可节省部分。可用“容量足够、保留全部兼容前缀”作可实现上界对照，确定改善空间。

第三步在受限 Qwen-Agent 真实工具闭环运行配对策略：无复用、LRU、retire-first LRU、固定 TTL、条件经验策略、GBDT 策略；相同模型／任务／到达序列／KV payload／工具线程／服务调度，先固定一组容量和并发验证，再报告容量与并发矩阵。策略顺序轮换、至少三次配对重复，并保存全部失败，不将只成功的策略批次挑出来比较。固定 TTL 只能在训练／开发工作负载选参数。

主指标为每题从 submit 到通过独立检查的最终答案的 JCT，报告配对均值、P50/P95、整批 makespan、成功率及逐题差值；副指标为请求 TTFT、真实 executed prefill、命中、队列／保护等待、预测／管理／观测开销。模型加载时间单列，试验期所有真实调度和预测开销都计入完成时间。改变策略可能改变输出和后续工具行为，须记录真实生成并逐策略做质量复核。

测试题现在已用于政策诊断；可以继续作为机制／性能开发集，但后续若基于这些结果选 horizon、容量、正则或策略公式，最终结论应在新冻结工作流或新批次确认。只有实际 JCT 降低、质量不退化且管理成本全部计入，才能宣称达到端到端目标。当前不应继续仅优化 Brier 或扩母题数量来替代这一系统闭环。
