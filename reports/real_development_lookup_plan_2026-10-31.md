# 下一阶段：真实开发中的工具代理误差、合法需求预测与缓存收益

执行状态更新：2026-11-01 的 [阶段 0 实测 Review](real_development_stage0_review_2026-11-01.md) 已交付，整体未通过，阶段 1 暂缓。下文的“尚未下载/执行”和资源快照均是 2026-10-31 制定计划时的历史状态；当前状态以 README 和最新 review 为准。

2026-10-31（Asia/Shanghai）。本文是接下来实验的执行顺序，优先于旧 D1–D10 计划中的扩量/建模顺序。**本次完成计划、现有结果归纳和机器资源核查；下述新采集、新训练和在线策略实验尚未执行。每完成一个阶段先 review，再决定是否进入下一阶段。**

主问题是：真实开发中，工具完成时间能否充分代理兼容前缀的下一次需求；如果不能，当时可见的信息能否预测差异，并在同一缓存决策器下减少真实服务成本。GBDT 是候选实现，既不是前提，也不是必须得到的结论。

## 1. 今天确认了什么

- 当前开发数据有 50 个母题、65 条可审计执行、472 个 episode、2,414 张快照。44 个母题来自 MBPP，95.8% 的 episode 小于 1 秒；3–10 秒只来自 3 个母题，自然 C=0，65 个 D 全部来自 runner 显式关闭。详见 [数据集说明](../docs/dataset_card.md)。
- [训练 v2](prediction_v2_50parents_review.md) 的完整集 0.1 秒 Brier 为全局经验 0.4986、条件经验 0.3889、GBDT 0.4317。GBDT 在已等待 ≥1 秒的少量快照上较好，尚不能推广到真实复杂工作负载。
- [冻结模型诊断](prediction_v2_diagnosis_and_next_steps.md) 发现实际编码仅有 19 个状态，所有 idle-start 快照只有 1 种状态；当前 GBDT 在训练内也落后。命令类别、工具状态、历史失败等已采字段尚未进入模型。现有结果不能证明“经验预测在一般情形下优于 GBDT”。
- CacheWise 的预测器是工具参数 TF-IDF/KMeans 聚类后的条件经验时长分布，并随 elapsed 更新剩余时间。论文从真实 Claude Code 会话采集 CATraces，再在 Qwen2.5-Coder-32B-Instruct 服务上确定性回放；不能将两步理解成“Claude Code 接 Qwen 32B 采集”。[原文 §5.2、§6.1](https://arxiv.org/html/2606.16824v1)
- 工具耗时可从客户端/工具执行器采集；我们的 U 是同一兼容前缀的真实 lookup，包括 miss，需要后端证据。lookup 时间用于监督标签，不是在线模型输入。更严格的标签不自动产生更大的系统收益。
- 现有 vLLM 探针已能记录实际 tokens、lookup 和请求释放边界块快照；缺口是多阶段关联、完整物理块生命周期、真实复杂开发覆盖和在线收益，不是从零建立采集链。

## 2. 要依次回答的四个问题

| 问题 | 需要的证据 | 不能代替它的证据 |
|---|---|---|
| H1a：真实开发中代理时间是否偏离需求时间？ | 同一 owner/上下文/已确定前缀上，工具/依赖结束到 request-ready、enqueue、lookup 的逐段观测；跨任务分布和未配对比例 | 工具耗时长、两个独立数据集的平均耗时不同 |
| H1b：差异是否影响实际决策？ | 容量压力下真实可淘汰候选的排序/动作改变，及独立策略运行的重算和完成时间 | 所有样本的平均时间差、只看排队对象、固定时间线回放收益 |
| H1c：差异是否可被在线信息利用？ | 不使用未来字段的预测器，在新任务/时间留出上利用可见阶段和依赖，改善同一决策器的结果 | 使用真实未来 lookup 的诊断策略有效 |
| H2：GBDT 是否比同样知情的条件经验更有价值？ | 相同训练数据、信息、切分和决策器下，概率/排序/系统收益及开销比较 | GBDT 独享新特征、随机拆快照、反复查看测试集调参 |

“经常出现”与“值得研究”分别回答：按 episode 计数之外，还报告按任务等权、按 idle KV 字节×时间、按真实淘汰决策加权的结果。少量长等待可能贡献大部分缓存压力；大量微秒差异也可能完全不影响决策。

H1a 不成立时收缩“工具代理不足”的主张；H1a 成立但 H1b/H1c 不成立时，不扩大复杂预测研究。它不意味着所有研究方向都不如 CacheWise，只表示这一条增量理由未获得支持。

## 4. 真实场景与数据来源

下一轮停止把增加 MBPP 母题作为主要扩量手段，采用两条明确分开的数据线。

**自然开发线：** 用户确实要做的功能、缺陷修复、重构和测试任务，由用户与本地 Agent 正常交互。保留真实追问、暂停、恢复、失败和放弃；记录活跃开发时间、会话开放时间和观察时长，不能为了方便把所有用户暂停截成 D。这一线回答现象是否存在及其覆盖范围，后续日期独立留出。只采集事先选定的实验工作目录和会话。

**可重复仓库任务线：** 固定公开仓库 commit、issue/需求、依赖环境、输入文件和独立验收，从未修改的 checkout 开始让 Agent 真实执行。优先在 aarch64 上能完整启动测试的 Python CLI/数据处理/HTTP 服务项目，随后再覆盖有稳定离线依赖的 JS/构建任务。具体仓库和 issue 在阶段 0 预检后冻结，不拿未安装成功的项目凑数量。任务源自实际需求；公开基准预训练暴露仍单独说明。

| 场景 | 自然操作 | 关注的可见状态 |
|---|---|---|
| 检索—修改—验证 | 文件搜索、代码编辑、局部测试、全量测试 | 命令类别、测试范围、已完成历史 |
| 失败—定位—修复 | 真实失败测试、查看 traceback、修改后重测 | 已观察失败、重试次数、工具返回状态 |
| 多阶段工程流程 | 类型检查、构建、测试、读取后台日志 | 当前阶段、已启动工具、输出可用状态 |
| 后台/并行依赖 | 任务确实需要时启动服务/构建，等待明确依赖 | 工具 ID、真实依赖边、结果交付与 join 状态 |
| 人工继续/上下文变化 | 用户追问、取消、恢复、压缩、分支 | owner/context version 的明确转换；不假定全部前缀失效 |

不使用 sleep 延长工具，不人为指定失败次数，不手工修复 Agent 的候选后冒充自主成功。保留失败、超时、接口问题和所有重跑原因；分别报告后端完整性、有效开发行为、独立任务验收。质量子集仅作补充，不能只保留成功任务再推断自然发生率。

阶段 0 先做 3–5 个任务、至少 2 个仓库的接入验证；阶段 1 的初始预算为 10–20 个独立真实任务、至少 3 个仓库，并观察约 5 个实际开发工作日的自然会话（依用户实际使用情况，不能用等待凑天数）。这些是工作预算，不是统计充分性保证；若独立任务少、秒级案例少或置信区间很宽，结论记为不足，扩大范围需另一次 review。

同一 issue、改写、规模变体、重跑和派生分支使用共同母题/来源组。阶段 1 用于探索；确定最终特征和指标后，再冻结未用于选择的仓库/任务与未来时间留出。仓库数不足时不强行声称 5 折跨仓库泛化，使用分组留出并报告实际支持范围。旧 50 母题保持开发数据身份。

## 5. 插桩与数据契约

复用旧探针的逻辑，新增独立的版本和导出器。当前 `d2_probe.py` 只验证了单卡、一个 full-attention cache group；`d2_dataset.py` 假定每次请求一个 lookup、正常结束、无抢占，并按旧 Chat Completions 请求 ID 关联。不能直接宣称它适配 Codex、TP、多次查找、抢占和并行 owner。

| 层 | 必须增加/确认的记录 |
|---|---|
| Agent/runner | task/session/owner/context version、turn/request/tool ID；真实工具 start/end、结果交付、请求 ready；已知依赖的创建/完成/取消；context close/restore/compact/fork 的语义和作用域 |
| 协议边界 | Agent 请求与引擎请求的一对一/一对多关系，重试和辅助请求用途，模板版本；不把重试当作独立任务，辅助请求不漏记 |
| 引擎 | 实际输入 token IDs、完整 compatibility/cache-salt 身份；enqueue、每次 lookup、抢占/恢复、scheduled prefill、正常 release/abort；同一 owner 后续兼容 lookup 不论 hit/miss 都可为 U |
| KV 管理器 | block hash 与物理 slot 的生命周期代次、分配/缓存插入/淘汰/释放、refcount、共享 owner、active/pin；容量和每次淘汰候选/动作；TP 逻辑事件去重，按 rank 记录物理内存，不能重复计算需求或漏计物理字节 |
| 观察器 | boot/进程身份、序号、单调时钟、观察范围、丢事件和异常退出；完整结束才支持 C。若跨主机，先做时钟对齐/误差界或保持主分析同机 |

idle 时按固定规则选定当时真实可缓存的完整前缀，禁止看到未来请求后倒选最长公共前缀。先延续“当前输入内最长完整 block 前缀”，对细粒度物理块另存映射；不要把这个长前缀未再使用误称为其所有子前缀都无需求。缓存策略比较在同一候选粒度进行，共享块的任何有效 owner 需求都必须进入物理决策，不能随意把某一 owner 的 D 变成全局块删除。

`retire` 是明确结束某个 owner–context version–前缀关系，不是缓存 eviction，也不是一次 turn 完成。会话仍可继续或恢复时维持开放；确实关闭旧关系才记录 D。压缩/分支只关闭有证据终止的关系。自然用户日志不保证有 D；禁止为凑类别定义“闲置 N 秒就死亡”。

原始 tokens/参数保存在本地受控数据目录，用于审计匹配；token 内容、关系 ID、未来时长/lookup/最终任务成绩不作为预测输入。可发布的摘要和哈希不能代替本地原始数据做端到端复现。普通云端 Codex 日志可供客户端代理分析，但没有服务端映射的部分不得进入主 U/D/C 集。

受控验收覆盖 cold/warm/evicted miss、共享前缀、分支/压缩、恢复、取消、抢占、请求重试、真实开放关系的 observation_end，以及事件断流拒绝。受控验收数据与自然发生率统计分开。测量探针开关的端到端差异；所有策略采用相同探针，另报告日志序列化/磁盘和预测开销。

## 6. 怎样测量“工具结束 ≠ 复用”

对可唯一关联的一组阻塞依赖，记录：

- `t_idle`：旧请求释放活动使用、预测前缀进入 idle。
- `t_tool_start/end`：每项工具的实际执行起止。
- `t_results_ready`：Agent 拿到此轮必要结果并满足实际依赖的时刻，包含后台输出读取与 join。
- `t_request_ready`、`t_enqueue`、`t_lookup`：客户端形成请求、服务接收、引擎实际查找。

串行单工具时，主要代理差为 `Δ = t_lookup - t_tool_end`。它可以拆成结果交付/依赖等待、客户端编排/传输和服务端排队/调度。总 idle 时长还包含工具启动前的间隔，**不能将工具持续时间直接与从 idle 起算的复用时间相减后就全部归因于工具结束后的延迟**。预测误差比较必须从同一个快照 `t0` 起算。

多工具时同时报告“单工具代理”和“整个必要依赖集合完成”的差异，给 CacheWise-style 对照提供相同的可见依赖信息，避免把错误选取一个短工具当成基线必然失败。当前可见依赖图可作为特征；通过未来日志重建出的实际关键路径只作离线解释。存在先 lookup 后后台工具完成时保留负差，不强塞入串行链。

没有唯一工具关联、期间前缀变更、D、C、人工等待的 episode 分别统计，不给它们补造工具结束或有限复用时间。报告工具代理的覆盖率及回退率；完整集中的未配对数据不能静默删除。

输出包含 1/10/100 ms、1/3/10 s 阈值发生率和分位数、任务/项目分层、Δ 相对 idle 时长的占比、各阶段占比，以及按 KV 占用和决策机会加权的结果。时间戳误差/探针开销内的差异不解释为真实机制。

特别分开三个状态：等待工具/依赖、结果已就绪但尚未提交、已经排队。active/已知 pending 请求按固定规则保护。若差异几乎全部来自已经受到保护的排队阶段，则不能据此证明淘汰预测更有用。负差、异常重排和未支持状态单列，先验证日志语义。

## 7. 阶段安排与 review 交付

| 阶段 | 范围与交付 | review 后的下一步 |
|---|---|---|
| 0：接入与完整性 | 独占资源窗口、模型与 Agent 协议验收；3–5 个真实任务；新版 ID/多卡/生命周期探针；工具、tokens、lookup、retire/C 的逐条样例及开销 | 链路完整、任务有有效操作后才扩大。若资源/协议未就绪，保留问题清单，不用模拟 lookup 代替 |
| 1：真实差异普查 | 自然线＋10–20 个仓库任务的探索预算；时间线、未配对率、Δ 分解、任务等权分布、候选资格和压力分层 | review H1a，并冻结最终评测定义。若仅看到无决策意义的延迟，缩小路线；证据不足不宣布阴性 |
| 2：最小决策价值 | 冻结缓存决策器；CacheWise-style 代理与实际 lookup 条件经验的对照；候选排序/动作、固定工作负载闭环实测，再做少量真实 Agent 策略复跑 | review H1b/H1c。只在未来信息诊断中获益时，结论为有空间但当前不可预测，不能直接扩训 |
| 3：公平模型比较 | 同一新数据上分开检验目标差异、信息差异与模型差异；训练折内预处理、有限开发搜索；独立任务/时间验证 | review H2；GBDT 没有稳定增量就保留条件经验。树模型失败不否定 lookup 目标本身 |
| 4：确认与复现 | 冻结后在未用于选择的任务/日期/项目和容量负载上确认；完整开销、任务质量、失败、偏移与恢复清单 | 输出可支持的结论范围和复现包，不把开发结果当生产泛化 |

阶段 1 采集时就记录容量/候选元数据；阶段 2 首轮在线实验只采用最小已验证的生命周期实现。若阶段 2 的因果模型尚无增益，但未来信息诊断与状态信号支持继续，则先 review，再进入有界的阶段 3 探索，而不是无限增加数据或调参。

## 8. 公平对照怎样设计

保留 LRU、开发集选择的固定 TTL 作为系统参照。预测器实验使用相同的可淘汰对象、active/pending 保护、共享块处理、容量、调度器、更新时间和决策规则；主对照固定调度器，避免把前缀调度改进归到预测器。没有实现 CacheWise 全部机制时标为 CacheWise-style predictor，不声称完整复现系统。

| 比较 | 固定的条件 | 改变的部分 | 能回答什么 |
|---|---|---|---|
| A：目标 | 共同工具名/完整参数表示/elapsed；相同条件经验容量与回退规则 | 工具完成时间代理 vs 合法 lookup 事件目标 | 直接需求标签是否有价值 |
| B：信息 | 相同 lookup 标签与条件经验方法 | 基础元数据 → 当前阶段/工具状态 → 已知依赖/历史/规模 | 哪些当时可见信号能解释差异 |
| C：模型 | 相同 lookup 标签、因果输入、训练/评测组和决策器 | 增强条件经验 vs 共享 GBDT | 树的共享和交互是否胜过合理分层统计 |
| D：系统 | 相同外部任务/资源预算和共同决策器 | 最终冻结的预测器 | 预测改善能否转化为净服务收益 |

A 先在有工具对应的 U 子集上比较相同起点/窗口下的需求时机，再单独报告全流量中的 D/C、无工具会话和覆盖。不能把工具预测器无 D 输出造成的差距全部称为“时间差收益”。完整系统对无工具/人工等待使用预先冻结的共同回退与关闭规则。

对照保留参数 TF-IDF 聚类和 elapsed 更新，参数只能来自当前已发布调用；词表、聚类、分箱、缩放和回退统计全在训练折拟合。条件经验使用层次回退/收缩，不能只用过细笛卡尔积制造稀疏失败；GBDT 使用相同信息，可学习连续时间和交互。前缀长度/工具规模须带单位；仓库、任务、owner、命令中的唯一文件名等身份信息不当作泛化捷径。

GBDT 的有界诊断首先在旧输入上检查容量/正则，再在新数据上比较共同增强输入。训练权重尺度与正则联动记录；不复用“depth=2、L2=10”就断言复杂场景也不适用。开发期限制候选配置数并预先记录，验证时不再选择参数；经验模型的分组/收缩也获得合理的开发预算。

预测指标以同一合法需求目标的累计多类 Brier、校准、支持覆盖和候选内排序为主；时长 MAE 仅在双方同起点、同结局的可比较子集报告。C 后未知标签不补成负例；无训练风险支持的窗口报告 unsupported 并同时列出排除量。样本有效性按独立任务/项目衡量，不用快照数假装扩大样本量。

## 9. 决策收益、因果边界与停止标准

先在真实可淘汰候选集上，用真实未来工具结束/lookup 分别构造离线诊断排序，记录排名、动作差异及潜在代价。二者都是 **未来信息诊断**，不进入线上模型，也不是证明全局最优收益的严格上界；单个未来启发式没收益，不足以证明任何策略都无空间。

阶段 2 采用两层服务端实验：

1. **固定工作负载的闭环重放。** 冻结某次真实轨迹的请求 token 序列、工具工作/外部等待和依赖；各策略从相同状态分别执行真实推理和 KV 动作。下一请求根据该次运行的响应完成与外部依赖推进，重新产生 lookup，不能照抄原轨迹绝对 lookup 时间。该层控制生成差异，属于固定工作负载系统实验，不代表 Agent 会在所有策略下自然生成完全相同动作。
2. **真实 Agent 端到端复跑。** 从相同任务初态和预算分别运行，保留策略导致的时序/生成/工具路径差异，报告任务成功率、实际工作量、失败和完成时间。不能只对成功完成且轨迹相似的运行做选择后比较。自然用户追问主要用于观察，不假装能精确重现人的行为。

两层都固定 workload mix、模型/精度/TP、调度器、容量与外部工具资源；策略执行顺序分块随机化，尽量使用配对任务并记录重复种子。先做无压力、适度压力、高压力三个开发容量点，容量和并发在最终测试前冻结；使用实际容量竞争，不通过 sleep 或偷改工具时长制造收益。多 Agent 并发与单任务内部依赖分别标注。

主系统指标为额外执行的 prefill/recomputation tokens（结合块驻留和请求内容判定）、总 prefill、真实 miss/淘汰量、KV 占用、端到端任务完成时间、尾延迟、token goodput 和任务质量。仅 `scheduled_prefill_tokens` 不是设备计算时间；需要时另记设备计时。明确自然新增 prompt 与因淘汰导致的重算，不能混为同一指标。报告包含预测/日志在内的总开销，以及不含人工/工具等待的服务端时间，避免与 CacheWise 的会话时间口径混淆。

预先建议的实际收益门槛：相对强工具代理，额外重算量降低至少 5%，且包含预测开销的完成时间没有实质恶化；GBDT 也用同样的净收益原则判断。5% 是待阶段 0/1 review 冻结的工程目标，不是已有结果或统计定律。若主要改善完成时间而非重算，须在最终测试前确定另一主指标，不能看结果后更换。阶段 0 确定观测开销容忍度和完成时间非劣界，再锁定。

按任务/项目聚类计算配对差异和置信区间，独立项目太少时明确只能探索；不要把数千快照当数千独立重复。至少在两个来源和两个有压力负载设置下检查一致性，同时保留无压力负对照。最终选择仍需新的冻结测试；少量任务没有显著差异时先看区间宽度，不把无显著性当等效。

| 观察到的结果 | 决定 |
|---|---|
| Δ 很小，或几乎全部在已保护/无压力状态 | 收缩“工具代理不足”主线，保留更简单的方法 |
| 有决策相关 Δ，但只有未来信息排序有效 | 检查可见状态是否缺失；有界补采后 review，不直接声称因果模型更好 |
| lookup 条件经验优于工具代理，GBDT 无增量 | 保留真实需求建模和条件经验，停止把 GBDT 作为主方法 |
| GBDT 在新任务/时间上稳定改善净收益 | 采用 GBDT，保留经验回退与偏移监测 |
| 区间过宽、场景覆盖不足 | 报告尚不能判断，依据缺口增加独立真实任务 |
