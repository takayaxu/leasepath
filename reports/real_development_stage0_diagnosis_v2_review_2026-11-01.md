## 2. 新接口、预算与冻结

[工具接口](../src/leasepath/real_tools_v3.py)、[runner](../scripts/run_stage0_diagnostics_v3.py) 和 [配置](../configs/prediction/real_development_diagnostic_v3.json) 单独版本化为 v3。工具提供编号行范围读取、可继续读取的完整输出分页、精确文本替换、diff 与显式测试命令。旧文本零匹配/多匹配、路径越界、无 diff 或 L1 范围外写入均拒绝；多项编辑在写入前全部校验。真实修改后使用任务解释器检查 Python 语法，保留实际错误及附近源码，不自动给正确补丁或调整缩进。

输出页按 tokenizer 计算，单页最多 3,500 token，记录 result_id、原始输出哈希、实际可见字符区间和省略区间。请求前精确计算模板化输入 token 并预留输出，超过 16K 在 HTTP 之前停止；无自动压缩、上下文重写或 HTTP 重试。每次响应、拒绝编辑、自动语法检查及显式测试分别留痕。读写/语法反馈 5 项针对性回归通过；全套 156 项通过。

冻结目录 `stage0-diagnosis-v2-20261101-preregistration/` 保存计划、源码、配置哈希、diagnostics.json 和只追加的诊断预算 ledger。每个条件/来源题只运行一次，基础设施无效尝试也保留且不自动重置预算。L1 每题 1 次调用、最多 4,096 输出 token、600 秒；L2/L3 每题最多 24 次调用、每次 2,048 输出 token、900 秒，单工具 90 秒。连续 3 次无效动作、3 次错误语法编辑或 10 次未改变补丁停止；绝对调用/时间上限始终保留。

三层都从干净 checkout、私有环境和新上下文开始。L1 给原 issue、完整相关函数/依赖上下文和原仓库已有测试，限定生产文件；L2 只增加文件位置；L3 不给定位。隐藏验收测试和参考修复不进入提示词。每层三题独立正确性至少 2/3 才推进下一层。L1/L2 均不是自主成功率。独立验收使用原先冻结 FAIL_TO_PASS 与相关完整测试文件，候选测试不能替代。

本轮最多两个模型配置、最多 21 次诊断。整体新接口不是单因素对照；不额外执行可选的 3 次旧接口配对，也不将旧失败当作新配对结果。不能将任何改善单独归功于精确编辑或分页。

## 4. 预选替代配置

条件触发的替代候选是已本地部署过的 **Qwen/Qwen3.8-27B**，在新成绩之前选定，依据是本机既有聊天/并发验收记录和 BF16 权重可用性，不是运行多个候选后择优。来源是 `/home/ma-user/work/qwen-services/models/qwen3.8-27b/`；上游 source-manifest 的顶层 revision 为 master，身份按其中逐文件 revision 和 SHA256 快照冻结，**不把 master 称为固定 commit**。30 个相关文件含全部权重分片的大小/哈希核验通过。

候选证据审计发现预登记引用了通用 `tool-calling-verification.json`，其中原生工具调用结果实际属于 coder390-q4 和 qwen3.5-9b，不能作为该 27B 的通过证据。原冻结文件保持不变，另存证据纠正。该 27B 的模板具备工具序列格式、旧服务证明可部署，但没有已核验的专门编码/原生工具能力基准。因此候选依据弱于计划优先考虑的明确代码/工具证据，应作为本轮选择限制，不能凭型号或模板补称已通过；本轮只测试文本 JSON 编辑接口，没有验证其原生 function calling。

使用独立设备 2/3、端口 8213、BF16 TP2、16K，text-only、思考输出关闭。首次生成前对比本地模板与服务 `/tokenize`，完整 token 序列一致。嵌套模型配置的 EOS=endoftext(248044)，tokenizer 的 EOS=im_end(248046)，因此首次生成前显式冻结两个 stop_token_ids。初稿替代配置和该预检修订都保留，之后不按答题结果再改配置。

该模型是混合注意力架构，已有 Qwen2 物理块验收不能直接移植。当前仅作为**本地离线能力对照**，服务未安装 leasepath 引擎钩子；诊断轨迹有前端身份但没有 backend owner/prefix 映射，不能进入主 U/D/C 数据集。若成为主链，必须另外验证新的 KV/生命周期、容量及探针开销。模型、模板、结束 token 和架构同时不同，比较的是模型服务配置，不能作参数量或某一接口因素的因果结论。

替代 run 为 `stage0-diagnosis-v2-20261101-alternative-a/`，每题一次新上下文，使用与当前模型相同的三题、可见源码/原测试及精确编辑接口，没有从当前候选补丁或评测反馈传递信息。结果如下：

| 题目 | 精确编辑与语法 | 独立测试 | 失败类型 |
|---|---|---|---|
| Flask-4992 | 替换成功，语法通过 | 18 passed、1 failed | 采用完整 Python 文件 mode 参数；冻结目标调用 canonical `text=False`，API 不匹配 |
| Flask-5063 | 替换成功，语法通过 | 53 passed、4 failed | 无条件新增 Domain 列，显示 subdomain 而未覆盖 host；目标失败并破坏两项旧输出回归 |
| pytest-9359 | 替换成功，语法通过 | 54 passed、1 failed | 调整装饰函数的 start，未修复前一 assert 的 end 仍包含后续 decorator 的目标问题 |

**替代 L1 仍为 0/3，停止其 L2/L3 分支，结束本轮。** 三次响应均 stop；当前模型三次也均 stop，六次新尝试都没有 length 截断或 context-budget stop。六次私有环境预检通过、无 HTTP 错误/隐式重试，实际 usage 的 prompt token 数与请求前计算一致。当前模型另有后端全 token IDs 核对，替代模型仅有模板预检的完整 IDs 和逐请求 usage 长度核对，不能混称相同完整性证据。

Flask-4992 的失败还需区分 API 契约：原 issue 示例给 `mode="b"`，冻结目标测试使用 `text=False`，不能把这一测试失败单独解释为完全不会二进制读取。事后隔离补充检查显示，两份候选以 `mode="rb"` 均能加载真实 TOML；但两者的 `mode="b"` 均报 ValueError，当前 32B 默认模式还破坏原读取回归。替代模型保留了 18 项旧测试，却仍未满足冻结 API。该 [补充诊断](../results/real_development/stage0_diagnosis_v2_2026-11-01/post-evaluation-api-diagnosis.json) 不反馈给模型、不改变预登记门槛、不把部分行为通过改记整题成功。

机械编辑结果有改善迹象：同一套新接口下，当前模型有两次原文零匹配，替代模型三次均能应用且语法通过；功能门槛没有改善为通过。它支持下一次规划关注 API/行为理解与回归保持，不能证明新接口因果有效，也不能证明更换模型已修复自主链。单次 L1 不含模型错误恢复调用，因而本轮不能评价 L2/L3 的反馈恢复能力。公开 benchmark 曝光、帮助范围和单次预算也限制解释。
